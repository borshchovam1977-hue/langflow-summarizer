# Описание бизнес-логики пайплайна Нормоконтроль

## 1. Прием запроса

Сервис принимает POST-запрос на эндпоинт `/api/v1/doc-control` со следующими параметрами:

- **file** — DOCX документ для обработки
- **request_id** — уникальный идентификатор запроса
- **mode** — режим применения изменений (`revision` или `comments`)
- **rules** — JSON-строка с перечнем правил и их настроек
- **model** — имя LLM модели (опционально)
- **client** — тип LLM клиента (`vllm`, `deepseek`, `openai`)
- **enable_llm_validator** — флаг включения LLM-валидатора
- **enable_re_validators** — флаг включения regex-валидаторов

**Важно**: Режим `modify` (прямое изменение документа) не поддерживается — система работает только в режимах`revision` (
tracked changes) и `comments`.

## 2. Чтение файла

Система извлекает байтовое содержимое загруженного DOCX файла.

## 4. Форматирование документа (docx_formatter)

Если в правилах указан `docx_formatter`:

1. Применяются настройки полей страницы (margins)
2. Устанавливаются параметры для параграфов (шрифт, межстрочный интервал, отступы, выравнивание)
3. Настраиваются стили заголовков
4. Применяются правила встроенного форматирования (bold, italic, underline)
5. При необходимости форматирование распространяется на таблицы

Результат — обновленный байтовый массив документа.

**Особенность**: Это единственное правило, которое применяется к байтам документа напрямую, без создания списка
corrections. Результат сразу становится новой версией документа для последующих этапов.

## 5. Подготовка структур данных

### 5.1. Открытие документа

Документ открывается как объект python-docx Document.

### 5.2. Создание плоского списка параграфов

Система извлекает все параграфы документа, включая параграфы внутри таблиц, формируя единый линейный список. Это
позволяет работать с документом как с последовательностью текстовых блоков независимо от их вложенности.

**Важно**: Порядок параграфов в плоском списке соответствует порядку обхода в глубину: сначала параграфы верхнего уровня
документа, затем параграфы внутри таблиц (по строкам, по ячейкам, включая вложенные таблицы). Этот порядок критичен для
корректной работы системы локализации изменений.

### 5.3. Конвертация в Markdown и разбиение на чанки

Для LLM-правил документ:

1. Конвертируется в Markdown через Pandoc:
    - Используется кастомный Lua-фильтр для постобработки
    - Удаляются элементы `<span class="mark">...</span>`
    - Извлекаются медиафайлы в отдельную директорию

2. Разбивается на чанки с помощью CustomMarkdownSplitter:
    - Минимальный размер чанка: 300 токенов
    - Максимальный размер чанка: 1000 токенов
    - Разбиение учитывает структуру заголовков
    - Сохраняется контекст заголовков для каждого чанка
    - При разбиении предпочитаются границы предложений (перенос строки, точка)
    - Мелкие чанки (< 300 токенов) объединяются с соседними

**Токенизация**: Для подсчета токенов используется энкодер `o200k_base`.

## 6. Применение текстовых правил

Следующие правила выполняются параллельно (асинхронно):

### 6.1. normalize_quotation_marks

Нормализация кавычек согласно выбранному стилю:

- Идентификация всех символов кавычек в документе
- Нормализация straight-кавычек в целевой стиль (например, «ёлочки»)
- Обработка вложенных кавычек
- Формирование списка изменений (paragraph, start, end, replacement, comment)

**Поддерживаемые стили**: guillemets_ru (« »), guillemets_fr, guillemets_de, curly_en (" "), single_curly_en (' '),
straight (" "), single_straight (' '), cjk_corner (「 」), cjk_corner_bold (『 』), angle (〈 〉), double_angle (《 》).

**Алгоритм**:

1. Все кавычки нормализуются с чередованием открывающих/закрывающих
2. Сохраняются апострофы внутри слов (O'Connor)
3. Сохраняются обозначения дюймов/футов после цифр (5" или 10')
4. Сохраняются одиночные обратные апострофы (`) как маркеры кода

### 6.2. convert_quarters_to_roman

Замена арабских обозначений кварталов на римские:

- Поиск паттернов типа "1 квартал", "2-й кв.", "3-го квартала" и т.д.
- Замена цифр на римские числа (I, II, III, IV)
- Сохранение регистра и окончаний слов
- Обработка разделителей (пробел, NBSP, дефис, тире)
- Формирование списка изменений

**Паттерн**: Распознаются числа 1-4 с необязательным порядковым суффиксом (-й, -го, -му и т.д.), за которыми следует
слово "квартал" в различных формах (квартал, квартала, кв., кв и т.д.).

### 6.3. expand_money_expressions

Раскрытие денежных выражений:

- Поиск паттернов "число + валюта"
- Парсинг числа (с учетом разделителей групп: пробел, NBSP, точка, запятая, подчеркивание)
- Преобразование числа в слова на русском языке
- Выбор правильной формы слова валюты (рубль/рубля/рублей)
- Форматирование числа с группировкой по тысячам (через тонкий пробел)
- Формирование строки вида "1 000 (одна тысяча) рублей"
- Формирование списка изменений

**Поддерживаемые валюты**: RUB (рубль, руб., р., ₽), USD (доллар, дол., $), EUR (евро, €), GBP (фунт, £), KZT (тенге,
₸), UAH (гривна, ₴), CNY (юань, ¥).

**Особенности парсинга чисел**:

- Различает разделители групп и десятичные разделители
- Обрабатывает как "1 000,50", так и "1,000.50"
- Игнорирует числа с десятичной частью (не раскрывает "100.50 руб")
- Применяет максимальный лимит значения (настраивается, по умолчанию 10 млрд)

### 6.4. rule_job_titles

Проверка капитализации должностей:

- Построение Aho-Corasick автоматов для поиска:
    - Ключевых слов должностей (директор, начальник, менеджер и т.д.)
    - Модификаторов (главный, старший, заместитель, ведущий и т.д.)
- Поиск последовательностей "модификатор + должность"
- Разрешение перекрытий (выбор наиболее полного совпадения)
- Проверка капитализации первого слова
- Формирование списка изменений

**Источники данных**:

- `core_job_titles_inflected.txt` — список должностей во всех падежах
- `pre_modifiers_inflected.txt` — список модификаторов во всех формах

**Алгоритм**:

1. Поиск всех вхождений ключевых слов (case-insensitive)
2. Для каждой найденной должности попытка найти модификаторы слева (до 4 слов)
3. Разделители между словами: пробел, дефис, тире, слэш
4. Слияние перекрывающихся или смежных совпадений
5. Проверка регистра первой буквы первого слова

## 7. Применение LLM-правил

Для LLM-правил выполняется более сложный процесс:

### 7.1. Формирование запросов к LLM

Для каждого активного LLM-правила:

1. **Подготовка промпта**:
    - Системный промпт загружается из файла (например, `rule1_no_descriptive_sentences.txt`)
    - Промпт содержит детальные инструкции, примеры и схему ответа
    - Все промпты используют XML-подобную структуру с тегами для организации информации

2. **Формирование пользовательского сообщения**:
    - Чанк текста оборачивается в теги `<text_markdown>...</text_markdown>`
    - Добавляются префикс и постфикс согласно настройкам
    - Для каждого чанка создается отдельный запрос

3. **Вызов LLM**:
    - Запрос отправляется через llm_client на эндпоинт `/text_generation_sync`
    - Указывается JSON-схема ожидаемого ответа (structured output)
    - Параметры: temperature=0.0, top_p=0.1
    - Все запросы для разных чанков выполняются параллельно (асинхронно)

4. **Сбор ответов**:
    - Для каждого чанка получается JSON с найденными проблемами
    - Формат ответа зависит от правила и режима:
        - Простая структура (режим revision): `{initial sentence, explanation, modified text}`
        - Структура с ошибками (режим revision):
          `{initial sentence, errors: [{exact location, explanation, modified text}]}`
        - Простая структура (режим comments): `{initial sentence, explanation}`
        - Структура с ошибками (режим comments): `{initial sentence, errors: [{exact location, explanation}]}`

### 7.2. Правила и их специфика

#### rule_no_descriptive_sentences

Ищет описательные предложения без функциональной нагрузки:

- Маркетинговые обороты ("современный мир", "инновационные решения")
- Эмоциональные конструкции ("мы заботимся", "для вашего удобства")
- Общие декларации без конкретных обязательств
- Субъективные оценки без измеримых параметров
- Возвращает список предложений для удаления

#### rule_text_brevity

Ищет декоративные языковые излишества:

- Избыточные синонимичные группы (3+ прилагательных без функции)
- Очевидные украшательства ("абсолютно полный", "в любой момент времени")
- Эмоционально окрашенные синонимы ("быстрый и незамедлительный")
- НЕ считает избыточными юридические повторы и перечисления
- Возвращает список предложений для упрощения

#### rule_syntax_and_spelling

Ищет технические ошибки:

- Повторы слов подряд ("может может", "иную иную")
- Пунктуационные ошибки:
    - Пропущенные точки в конце завершенных предложений
    - Лишние запятые
    - Несколько финальных знаков препинания (.., !!, !?)
- Орфографические ошибки (опечатки, неправильные окончания)
- Незавершенные грамматические конструкции (предложение заканчивается на "включая", "в том числе" и т.п.)
- Возвращает список ошибок с точным указанием фрагмента

#### rule_capitalization (альтернативный алгоритм)

Проверяет капитализацию должностей:

- Ищет наименования должностей после маркеров ("Ответственный:", "Должность:", "Роль:")
- После управленческих глаголов ("назначить", "утвердил", "подписал", "является")
- После фраз "обязанности исполняет", "исполняет обязанности"
- После сокращений ("и.о.", "зам.")
- В перечислениях, разделенных запятыми или союзами
- Проверяет, что первое слово должности с заглавной буквы
- Возвращает список ошибок капитализации

## 8. Пре-валидация регулярными выражениями

Если `enable_re_validators=True`, применяются два валидатора:

### 8.1. Валидатор синтаксических правил

Для `rule_syntax_and_spelling`:

- Проверяет объяснения (explanation) на совпадение с фразой "Пропущена точка в конце предложения"
- Если фраза найдена, проверяет поле exact location:
    - Убирает trailing whitespace (пробелы, NBSP, thin space и т.д.)
    - Проверяет последний символ на принадлежность к stop_punct (., !, ?, …)
    - Если точка уже есть — исправление считается некорректным и удаляется
- Используется регулярное выражение для проверки trailing whitespace

### 8.2. Валидатор капитализации должностей

Для `rule_capitalization`:

- Извлекает название должности из объяснения:
    1. Ищет фразу "Первое слово должности «...» должно быть с заглавной буквы"
    2. Извлекает текст между кавычками (поддерживаются «», „", "", '', ())
    3. Если основной паттерн не срабатывает — использует fallback поиск любых кавычек
- Проверяет, что в исходном предложении (initial sentence) это слово действительно написано с маленькой буквы:
    1. Ищет совпадение case-insensitive
    2. Проверяет первый алфавитный символ найденного совпадения
    3. Если он уже заглавный — исправление некорректно
- Удаляет исправления, где первая буква уже заглавная

## 9. LLM-валидация

Если `enable_llm_validator=True`, выполняется дополнительная валидация:

### 9.1. Сбор всех исправлений

Все исправления от целевых LLM-правил собираются в единую структуру. По умолчанию проверяются:

- `rule_no_descriptive_sentences`
- `rule_text_brevity`
- `rule_syntax_and_spelling`
- `rule_capitalization`

### 9.2. Формирование групп для валидации

- Каждое исправление нумеруется (сквозная нумерация)
- Для каждого исправления формируется XML-блок и подсчитываются токены
- Исправления, превышающие лимит токенов на группу (15000 токенов), отфильтровываются и помечаются как oversized
- Оставшиеся исправления распределяются по группам с использованием жадного bin-packing алгоритма:
    1. Исправления сортируются по размеру (от большего к меньшему)
    2. Вычисляется минимальное количество групп (total_tokens / limit)
    3. Для каждого исправления выбирается группа с наименьшей текущей загрузкой
    4. Если исправление не помещается ни в одну группу — увеличивается количество групп
    5. Процесс повторяется пока все исправления не будут распределены

### 9.3. Построение промпта валидатора

Для каждого исправления создается XML-блок вида:

```xml

<entry number="N">
    <rule>имя_правила</rule>
    <sentence>исходное предложение</sentence>
    <comment>объяснение</comment>
    <fragment>точный фрагмент</fragment>
    <suggested_change>предлагаемое изменение</suggested_change>
</entry>
```

Все блоки группы оборачиваются в контейнер:

```xml

<review>
    <entry number="1">...</entry>
    <entry number="2">...</entry>
    ...
</review>
```

Этот XML-блок становится пользовательским сообщением для валидатора.

### 9.4. Вызов LLM-валидатора

- Системный промпт содержит строгие критерии валидности
- LLM проверяет каждое исправление по следующим правилам:

**Обязательные проверки для всех правил**:

1. **no_issue_claim**: Если в comment содержится утверждение об отсутствии проблем ("нарушений нет", "ошибок не
   найдено", "соответствует требованиям", "корректно", "оставить без изменений" и т.п.) — исправление некорректно

**Дополнительные проверки**:

2. **fragment_presence**: Если fragment указан, он должен присутствовать в sentence (после нормализации пробелов)

**Для rule_syntax_and_spelling**:

3. **punctuation_missing_dot**: Если заявлено "пропущена точка", а sentence или fragment уже завершается точкой —
   некорректно
4. **punctuation_extra_marks**: Если заявлены "лишние знаки", а fragment не содержит повторных знаков в конце —
   некорректно
5. **word_repeat_adjacent**: Если заявлен "повтор слова", а fragment не содержит двух соседних одинаковых слов —
   некорректно

**Для rule_capitalization**:

6. **capitalization_first_lexeme**: В fragment находится первая буквенная лексема. Если её первый символ заглавный или
   вся лексема в UPPER CASE — некорректно

- Параметры вызова: temperature=0.05, top_p=0.95, structured output
- LLM возвращает JSON: `{invalid_numbers: [1, 5, 7, ...]}`
- Все группы валидируются параллельно с ограничением конкурентности (по умолчанию 8 одновременных запросов)

**Презумпция корректности**: Если однозначно выявить противоречие невозможно — исправление считается корректным.

### 9.5. Удаление некорректных исправлений

- Для каждого номера из `invalid_numbers`:
    1. Находится соответствующее исправление
    2. Из JSON-структуры удаляется:
        - Если есть массив `errors` — удаляется конкретная ошибка
        - Если ошибок не осталось — удаляется весь объект sentence
        - Если `errors` нет — удаляется весь объект sentence
    3. Обновляется JSON-payload для соответствующего правила и чанка
- Ведется подсчет удаленных исправлений

## 10. Планирование изменений от LLM-правил

Для каждого LLM-правила выполняется планирование:

### 10.1. Парсинг JSON-ответов

Для каждого чанка:

- Парсится JSON структура
- Извлекаются поля: `initial sentence`, `exact location`, `explanation`, `modified sentence`
- Различается два формата:
    - Простой: sentence содержит explanation и modified sentence напрямую
    - С ошибками: sentence содержит массив errors, каждая ошибка имеет exact location, explanation, modified text

### 10.2. Поиск фрагментов в документе

Для каждого исправления:

1. **Поиск абзаца через fuzzy-matching**:
    - Используется RapidFuzz WRatio для поиска абзаца, наиболее похожего на `initial sentence`
    - Для каждого абзаца:
        - Склеиваются все предложения абзаца (из para_sentences)
        - Вычисляется score = fuzz.WRatio(target.casefold(), joined.casefold())
        - Выбирается абзац с максимальным score
    - Порог сходства: 80 (настраивается через DEFAULT_THRESHOLD)
    - Если лучший score >= threshold и best_idx найден — используется этот абзац
    - Если best_idx == -1 или best_score < threshold — переходим к fallback-локатору

2. **Fallback-локатор** (RobustTextLocator):
    - Применяется только если fuzzy-matching не дал результата
    - Сканирует все абзацы документа (плоский список)
    - Для каждого кандидата (сначала fragment, затем target) применяет каскад стратегий:

      **Базовые стратегии**:
        - Case-sensitive поиск
        - Case-insensitive поиск
        - Поиск с гибкими пробелами (flexible whitespace — поддержка Unicode whitespace)

      **Варианты текста**:
        - Исходный текст
        - Текст без markdown-выделения (**...**)
        - Текст без markdown-заголовков (# ...)
        - Текст без заголовков и без выделения
        - Текст с обрезанными кавычками и финальной пунктуацией

    - Для каждого варианта применяются все три базовые стратегии
    - Возвращается первое найденное совпадение
    - Если fragment найден — используется его позиция, иначе пробуется target
    - Если ничего не найдено — исправление пропускается с предупреждением в логе

3. **Уточнение контекста** (если абзац найден):
    - В найденном абзаце ищется точный контекст (`initial sentence`)
    - Используется функция `_locate_context_range`:
        - Сначала точный поиск
        - Затем case-insensitive
        - Затем flexible whitespace поиск
        - Также пробуются варианты с удалением markdown-маркеров
    - Если контекст не найден — проверяется растяжение на несколько абзацев:
        1. Проверяются комбинации: [prev, current], [current, next], [prev, current, next]
        2. Тексты абзацев склеиваются через пробел (с нормализацией переносов строк)
        3. Ищется normalized_target в склеенном тексте
        4. Если найдено — используется весь текущий абзац как контекст
        5. Если контекст не найден вообще — используется весь текст абзаца (0, len(text))

4. **Поиск точного фрагмента**:
    - Внутри найденного контекста ищется `exact location`
    - Используется функция `_locate_fragment_in_segment`:
        - Поддерживается tracking использованных диапазонов (избегание дублирования)
        - Применяются те же стратегии: case-sensitive, case-insensitive, flexible whitespace
        - Пробуются варианты с удалением markdown-маркеров
        - Функция `_first_non_overlapping` выбирает первое вхождение, не перекрывающееся с уже использованными
    - Если fragment не найден в сегменте — ищется в полном тексте абзаца
    - Если и там не найден — используется fallback-локатор для fragment отдельно
    - Если fragment не указан — используются границы контекста

## 11. Валидация и разделение изменений

### 11.1. Валидация диапазонов

Для каждого исправления проверяется:

- Индекс абзаца находится в пределах документа (0 <= paragraph < len(flat_pars))
- start и end корректны (start >= 0, end > start)
- end не выходит за границы текста абзаца (end <= len(par.text))

Некорректные исправления отфильтровываются и не попадают в финальный список.

### 11.2. Разделение по режиму применения

**Для режима COMMENTS**:

- Все исправления преобразуются в комментарии

**Для режима REVISION**:

- Исправления сортируются по абзацам и позициям (paragraph, start, end)
- Выявляются перекрывающиеся изменения в каждом абзаце:
    1. Для каждого абзаца создается отдельный список изменений
    2. Список сортируется по start (при равенстве — по end)
    3. Отслеживается last_end — конец последнего обработанного изменения
    4. Если start текущего изменения < last_end — это перекрытие
    5. Перекрывающееся изменение преобразуется в комментарий:
        - delivery_mode меняется на "comment"
        - replacement_text сбрасывается в None
        - В comment_text добавляется пояснение "Overlapping change from rule '...'"
    6. Неперекрывающееся изменение сохраняется как revision
    7. last_end обновляется до end текущего изменения

**Результат**: Два списка — revisions_corrections и comments_corrections.

### 11.3. Группировка комментариев по авторам

Комментарии группируются по парам (paragraph, author), чтобы корректно применить многоавторские комментарии к одному
диапазону текста:

- Создается структура: `{(paragraph_idx, author): [change1, change2, ...]}`
- Это позволяет в одном проходе обработки абзаца вставить все комментарии всех авторов
- При перестроении абзаца комментарии разных авторов корректно размечаются XML-элементами

## 12. Применение изменений к документу

### 12.1. Применение комментариев

Если есть комментарии для вставки:

1. **Группировка комментариев**:
    - Комментарии группируются по парам (номер абзаца, автор)

2. **Для каждого абзаца с комментариями**:

   a. **Сохранение структуры текста**:
    - Запоминается каждый символ абзаца вместе с его форматированием
    - Создается список пар: (символ, стиль)

   b. **Проверка и корректировка границ**:
    - Диапазоны комментариев проверяются и корректируются при необходимости

   c. **Создание объектов комментариев**:
    - Для каждого диапазона создается комментарий с уникальным идентификатором
    - Фиксируется автор, текст и временная метка (UTC)

   d. **Перестроение абзаца**:
    - Все runs абзаца удаляются
    - Абзац строится заново посимвольно:
        - Вставляются XML-маркеры `w:commentRangeStart`
        - Каждый символ воссоздается с сохранением форматирования
        - Вставляются XML-маркеры `w:commentRangeEnd` и `w:commentReference`

   e. **Верификация**:
    - Проверяется идентичность текста до и после перестроения

### 12.2. Применение revisions (tracked changes)

Если есть правки для отслеживания:

1. **Оптимизация правок**:
    - Соседние правки с одинаковым автором и комментарием объединяются
    - Между ними должны быть только пробелы и знаки препинания

2. **Обработка перекрывающихся правок**:
    - Перекрывающиеся правки уже преобразованы в комментарии
    - Их диапазоны корректируются для размещения в видимом тексте

3. **Для каждого абзаца с правками**:

   a. **Сохранение структуры текста**:
    - Запоминается каждый символ с полным форматированием (включая bold/italic)

   b. **Перестроение абзаца**:
    - Все runs абзаца удаляются
    - Абзац строится заново с последовательным применением правок:

      **Для каждой правки**:
        - Воссоздаются символы до начала правки
        - Вставляются маркеры начала комментариев (если есть перекрытия)
        - Для удаленного текста: вставляется `w:del` блок с автором, временем и текстом
        - Для добавленного текста: вставляется `w:ins` блок с автором, временем и текстом
        - Вставляются маркеры конца комментариев (если есть перекрытия)
        - Воссоздаются оставшиеся символы

4. **Генерация идентификаторов**:
    - Каждому блоку присваивается уникальный номер (последовательно от 1)

5. **Временные метки**:
    - Все изменения получают одну метку времени (UTC, ISO 8601)

**Важно**: Перестроение абзацев необходимо для корректной вставки XML-элементов отслеживания изменений (`w:ins`,
`w:del`) и комментариев (`w:commentRangeStart/End`) в требуемые позиции документа.

### 12.3. Сохранение документа

Модифицированный документ сохраняется в память как байтовый массив.

## 13. Построение метаданных

Для каждого примененного правила формируется метаинформация:

### 13.1. Сбор статистики

Для каждого правила:

- Статус выполнения (ok: bool) — True, если правило выполнено успешно
- Количество применённых изменений (count: int)

**Источники данных**:

- Для текстовых правил — количество corrections в списке
- Для LLM-правил — количество corrections в списке
- Для docx_formatter — 1 если документ изменился, 0 если нет

### 13.2. Извлечение фрагментов

Для каждого correction (кроме `docx_formatter`):

1. **Получение текста абзаца**:
    - Используется оригинальный документ (до применения изменений)
    - Из плоского списка абзацев извлекается paragraph по индексу
    - Получается текст: `par.text or ""`

2. **Построение фрагмента контекста**:
    - Используется алгоритм извлечения фрагмента с минимальной длиной (6 символов без пробелов)
    - Алгоритм работает следующим образом:

      a. **Определение границ строки**:
        - Находятся ближайшие переносы строк слева и справа от pivot-позиции
        - line_bounds = (left_bound, right_bound)

      b. **Поиск ближайшего токена (anchor)**:
        - От pivot двигаемся влево и вправо до ближайшего не-пробельного символа
        - При равном расстоянии выбирается правый
        - Не пересекаем boundaries строки

      c. **Определение span токена**:
        - От anchor расширяемся влево и вправо, пока встречаются не-пробельные символы
        - Получаем [start, end) для одного токена

      d. **Нормализация границ**:
        - Если start попадает внутрь токена — сдвигаем к началу токена
        - Если end попадает внутрь токена — расширяем до конца токена

      e. **Расширение до min_length**:
        - Подсчитываем не-пробельные символы в [start, end)
        - Если меньше min_length — расширяем:
            - Чередуем направления (влево/вправо)
            - На каждом шаге берем целый токен + preceding/following пробелы
            - Не пересекаем границы строки
            - Останавливаемся, когда достигнут min_length или блокированы оба направления

    - Для правила quotation_marks используется специальный алгоритм:
        - Сначала ищется позиция первого символа кавычки в диапазоне
        - От него применяется основной алгоритм с pivot на этой позиции
        - Если кавычка не найдена — используется обычный алгоритм для диапазона

3. **Формирование записи**:
   ```json
   {
     "fragment": "контекст вокруг изменения",
     "comments": "объяснение изменения"
   }
   ```

**Особенности**:

- Фрагменты не содержат переносов строк (ограничение line_bounds)
- Минимальная длина обеспечивает достаточный контекст для понимания
- Фрагменты состоят из целых токенов (не режутся посередине слова)

### 13.3. Структура meta.json

```json
{
  "rules": {
    "docx_formatter": [

    ],
    "normalize_quotation_marks": [

## 14. Формирование ответа

### 14.1. Создание ZIP архива

В памяти создается ZIP архив, содержащий:

1. **Обработанный DOCX файл**:
    - Имя: `{original_name}_processed.docx`
    - Если формирование имени не удалось — используется `document_processed.docx`
    - Содержимое: результат всех примененных правил

2. **Файл метаданных**:
    - Имя: `meta.json`
    - Содержимое: JSON с детальной информацией о примененных правилах
    - Кодировка: UTF-8
    - Формат: компактный JSON без пробелов

### 14.2. Формирование HTTP-ответа

Возвращается StreamingResponse с:

- **Content-Type**: `application/zip`
- **Headers**:
    - `Content-Disposition`: attachment с корректно экранированным именем файла
        - Формат: `attachment; filename="название.zip"; filename*=UTF-8''название.zip`
        - Поддержка UTF-8 для нелатинских символов
    - `X-Content-Type-Options`: nosniff (защита от MIME sniffing)
    - `Cache-Control`: no-store (запрет кеширования для безопасности)
- **Body**: ZIP архив как байтовый поток (BytesIO)

**Обработка ошибок на уровне эндпоинта**:

- 400 (Bad Request): невалидные параметры, ошибка парсинга JSON
- 500 (Internal Server Error): ошибки обработки документа

```

  ├─ rule_syntax_and_spelling

  ├─ Валидатор синтаксических правил
  └─ Валидатор капитализации должностей →

  ├─ Группировка исправлений
  ├─ Параллельная валидация групп
