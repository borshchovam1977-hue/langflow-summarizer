# Технические детали реализации RAG-системы на RRNCB бенчмарке

## Архитектура и стек моделей

Система построена на архитектуре RAG (Retrieval-Augmented Generation) с локальным развертыванием (on-premise).

### LLM (Large Language Model)

- **Модель**: Qwen3-30B-A3B-Instruct-2507
- **Параметры генерации**:
  - Temperature: 0.7
  - Top P: 0.9
  - Max tokens: 4096
  - Presence Penalty: 0.0
  - Frequency Penalty: 0.0
  - Context window: 32768 токенов
- **Квантование**: fp8

### Модель векторизации

- **Модель**: Qwen3-Embedding-8B
- **Размерность**: 4096
- **Квантование**: Q8_0

### Модель переранжирования

- **Модель**: Jina Reranker v2 Base Multilingual
- **Тип**: Cross-Encoder для вторичной оценки релевантности пар "вопрос-документ"
- **Max input length**: 1024 токенов с поддержкой sliding window для длинных текстов

### Комментарий

Для векторизации используется Qwen3-Embedding-8B, для переранжирования — Jina Reranker v2 Base Multilingual. Обе модели показывают высокие результаты на публичных мультиязычных тестах, а команда R&D дополнительно проверила их на юридическом корпусе на русском языке и подтвердила лучшее соотношение качества, стабильности и затрат на обработку запросов для наших задач.

В качестве основной языковой модели выбрана Qwen3-30B-A3B-Instruct-2507. Она сочетает достаточное количество параметров (30 миллиардов) с современной архитектурой и качественной настройкой под инструкции, что позволяет надёжно решать сложные многошаговые задачи, эффективно работать с длинным контекстом и формировать структурированные, понятные ответы в юридической и бизнес-областях. Размер модели и возможность сжатия до fp8 обеспечивают приемлемую скорость ответа и разумные затраты на обработку, что делает её подходящей для постоянной работы в качестве основного генеративного ядра RAG-системы.

Такая архитектура позволяет эффективно масштабировать систему в закрытом контуре без зависимости от внешних API, сохраняя контроль над данными и предсказуемость затрат при росте нагрузки.

## Пайплайн обработки запроса

Реализован двухступенчатый поиск для повышения precision/recall:

### Retrieval

Используется гибридный поиск (векторный + полнотекстовый BM25):

- **Векторный поиск**: Redis Vector Store с косинусным сходством
- **BM25**: Полнотекстовый поиск по локальному docstore
- **Веса**: Баланс семантика/полнотекст настраивается через QueryFusionRetriever (50/50)
- **Фильтрация кандидатов**:
  - Threshold: порог косинусного сходства (0.7)
  - Top K: количество кандидатов от каждого ретривера (20)
- **Fusion**: QueryFusionRetriever объединяет результаты обоих поисков следующим образом:
  - **num_queries=5**: Система автоматически генерирует 5 вариантов (переформулировок) исходного запроса. Например, для юридического вопроса о штрафах может быть сгенерирована переформулировка о санкциях, наказаниях, финансовых взысканиях и т.д.
  - **Обработка каждого варианта**: Для каждого из 5 вариантов запроса:
    - Векторный retriever возвращает топ-20 узлов
    - BM25 retriever возвращает топ-20 узлов
    - Результаты объединяются и дедуплицируются
  - **similarity_top_k=40**: Из объединённых результатов всех 5 вариантов система выбирает топ-40 узлов. Это обеспечивает хороший баланс между полнотой поиска (охватываем документы, найденные разными методами) и управляемостью (не перегружаем следующий этап)
  - **Результат**: На выходе fusion retriever-а — 40 лучших кандидатов, которые затем передаются в reranker для финальной очистки

### Reranking

Отобранные кандидаты передаются в Reranker:

- **Top N**: Similarity Top K = 10 (финальное количество чанков для LLM)
- **Цель**: Отсечение шума, оставление только наиболее релевантных чанков

### Generation

Оставшиеся чанки подаются в промпт модели вместе с системными инструкциями:

- **Промпт**: Кастомный шаблон с инструкциями по точности и форматированию
- **Режим**: SIMPLE_SUMMARIZE для подробных ответов
- **Параметры сэмплирования**: Temperature 0.7 для баланса креативности и точности, Frequency Penalty отключен

## Хранение данных

- **Векторное хранилище**: Redis с кастомной схемой (dimensions=4096, distance="cosine")
- **Локальный docstore**: SimpleDocumentStore для BM25
- **Чанки**:
  - **SentenceSplitter** (основной): 1500 символов + 300 перекрытие (≈500 токенов). Простое разбиение текста на чанки фиксированного размера с перекрытием для сохранения контекста между чанками.
  - **StructuralNodeParser** (альтернативный): 1000-2000 символов (≈333-667 токенов) с пресетом для средних документов (500-1000 токенов). Это наша собственная разработка продвинутого парсера, сохраняющего структурную целостность документа (секции, списки, таблицы), предотвращающего разрыв кодовых блоков и формул, с многопроходной балансировкой размеров. Позволяет добиться высокой точности на сложных документах за счет сохранения семантической связности и иерархической структуры.
  
  Выбор метода чанкинга осуществляется ситуационно в зависимости от типа документов: SentenceSplitter для простых текстов, StructuralNodeParser для сильно структурированных документов (юридические тексты, техническая документация). StructuralNodeParser поддерживает адаптивные настройки размеров чанков для разных сценариев:
  - **Короткие фрагменты** (300-500 токенов): для точных запросов и высокой точности
  - **Средние документы** (500-1000 токенов): сбалансированный режим для большинства задач
  - **Длинные контексты** (800-1000 токенов): для комплексного анализа и reranking
  - **Максимальный контекст** (до 1000+ токенов): для глубокого понимания сложных документов
  
  Это позволяет добиться высоких результатов на разных типах документов за счет оптимального сохранения семантической связности.

## Оценка качества

- **Метрики**: ROUGE-1, ROUGE-2, ROUGE-L, Answer Correctness, Semantic Similarity
- **LLM-as-judge**: Для субъективной оценки качества ответов по трем критериям:
  - **Correctness**: Сравнение с эталонным ответом (содержит ли ключевую информацию, нет ли ошибок)
  - **Completeness**: Полнота ответа (отвечает ли на все аспекты вопроса)
  - **Faithfulness**: Верность источнику (отсутствие галлюцинаций, все факты из контекста)

### Промпты для LLM-as-judge

#### Correctness

```plain
Ты - эксперт по оценке качества ответов на вопросы. Твоя задача - определить, является ли ответ системы корректным.

Вопрос: {question}
Эталонный ответ: {reference}
Ответ системы: {response}

Оцени, является ли ответ системы корректным по сравнению с эталонным ответом. Ответ считается корректным, если:
1. Содержит ключевую информацию из эталонного ответа
2. Не содержит фактических ошибок
3. Отвечает на заданный вопрос

Ответь ТОЛЬКО одним словом: "CORRECT" или "INCORRECT"
```

#### Completeness

```plain
Ты - эксперт по оценке качества ответов. Твоя задача - определить, является ли ответ полным.

Вопрос: {question}
Ответ системы: {response}

Оцени, является ли ответ полным. Ответ считается полным, если:
1. Отвечает на все аспекты вопроса
2. Предоставляет достаточно информации для понимания
3. Не оставляет важные части вопроса без ответа

Ответь ТОЛЬКО одним словом: "COMPLETE" или "INCOMPLETE"
```

#### Faithfulness

```plain
Ты - эксперт по оценке качества RAG-систем. Твоя задача - определить, основан ли ответ только на предоставленном контексте.

Контекст (найденные чанки): {chunks}
Ответ системы: {response}

Оцени, все ли факты в ответе можно найти в контексте. Ответ считается верным источнику, если:
1. Все факты и утверждения подтверждены контекстом
2. Нет добавленных фактов, которых нет в контексте
3. Нет искажения информации из контекста

Ответь ТОЛЬКО одним словом: "FAITHFUL" или "UNFAITHFUL"
```

### Конфигурация LLM-as-judge

**Модель**: Используется та же модель Qwen3-30B-A3B-Instruct-2507, что и для основной генерации ответов.

**Параметры оценки**:

- **Temperature**: 0.0 — минимальная случайность для максимально объективных решений
- **Max tokens**: 10 — ограничение на размер ответа (достаточно для бинарных решений)

**Методологическое примечание**:
Использование одной и той же модели для оценки ответов, которые она же генерирует, является нечастой практикой в исследованиях RAG. Обычно для избежания потенциального bias модели используют разные модели для генерации и оценки. Однако в нашем случае, согласно результатам внутреннего human evaluation, данный подход показывает хорошую корреляцию с оценками экспертов на русскоязычных юридических текстах и позволяет избежать несогласованности в критериях оценки. Это предполагает, что Qwen3-30B-A3B-Instruct-2507 достаточно компетентна для объективной самооценки в контексте этой специфической задачи, а главное это позволяет решить задачу оценки максимально бюджетно.

## Промптинг и системные инструкции

### Кастомный промпт для генерации ответов

Система использует детализированный промпт на русском языке с четкими инструкциями:

```plain
Ты — экспертный AI-ассистент, работающий строго по предоставленной базе знаний. Твоя задача — дать точный и исчерпывающий ответ на вопрос, основываясь ИСКЛЮЧИТЕЛЬНО на предоставленном контексте.

Инструкции:
1. Анализ: Внимательно проанализируй вопрос и найди в контексте факты
2. Точность: Не добавляй информацию из общей памяти
3. Фокус: Извлекай только конкретные детали
4. Честность: Если информации нет, так и напиши
5. Структура: Оформляй удобно для чтения
6. Объем: Давай развернутый ответ
7. Ссылки: Не включай ссылки на сторонние ресурсы
```

### Режим генерации

- **ResponseMode**: SIMPLE_SUMMARIZE для подробных ответов
- **Use async**: Включен для параллельной обработки

## Скрипты обработки данных

### Предобработка PDF перед разбиением на чанкингом

Предобработка PDF в нашей системе работает просто и последовательно: мы начинаем с PDF-файлов, которые содержат тексты законов, и конвертируем их в удобный Markdown-формат с помощью специальной библиотеки Docling. Она сохраняет всю структуру документа — заголовки, списки и даже таблицы в виде HTML-кода, чтобы ничего не потерять. Потом мы отдельно обрабатываем эти таблицы: используем искусственный интеллект (LLM), чтобы превратить их в понятный читаемый текст, без сложных ячеек и колонок. В конце мы проверяем и форматируем все Markdown-файлы с помощью линтера, чтобы они были аккуратными и без ошибок. Всё это делается автоматически, пакетами файлов, с прогресс-барами, чтобы видеть, как идёт работа.

## Производительность и оптимизации

Система построена с упором на высокую производительность и эффективное использование ресурсов. Для обработки запросов используется асинхронная архитектура на базе asyncio с контролем конкурентности через семафоры (по умолчанию до 10 одновременных задач), что позволяет эффективно распараллеливать операции без перегрузки инфраструктуры. Векторизация документов выполняется пакетами по 32 элемента, что оптимизирует использование GPU и снижает накладные расходы на обмен данными, а контекстное окно в 32768 токенов даёт возможность обрабатывать объёмные юридические документы без лишней фрагментации. Для хранения и поиска применяется Redis Vector Store, обеспечивающий быстрый доступ к векторным представлениям, а полнотекстовый поиск реализован через BM25-индекс также в Redis, что упрощает инфраструктуру и снижает задержки при гибридном retrieval.
